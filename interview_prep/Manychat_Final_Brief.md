## 3. Мої дві справжні проблеми — не знання

Підтверджені **двічі незалежно**: у моєму прогоні і в моку в іншому чаті.

**Причина 1 — не тримаю структуру.**
- Q4 у моку: відповів `a` / `ab` / `abc`. Функція повертає **списки**: `['a']`, `['a','b']`, `['a','b','c']`.
- D2: `[["X"], ["."]]` замість `[['X','.'], ['.','.']]`.
- D19: розплющив `(3,4)` замість вкладеного кортежу.

→ **Порахувати елементи і назвати стільку ж.** `()` і `{}` — це елементи.

**Причина 2 — не поширюю власний висновок.**
- Мок Q13: сказав `a is b` → `True`, і тут же вивів різні значення для `a` і `b`.
- D18: те саме, слово в слово, за кілька годин до того.

→ **Сказав висновок — перечитати свою відповідь і викинути суперечності.** Вголос:
*"wait — if those are the same object, my earlier answer was wrong, it's actually…"*.
Самокорекція дає **плюс**. Суперечність, що стоїть, — мінус.

**Причина 3 — фікс має запускатись.** `lambda i: i` (TypeError), `self.items = items` з None
(AttributeError), `items.pop()` замість reset, `fetch_all` без `return`.
→ **Назвати символ, який змінив.** Не можеш назвати — фіксу немає.

**Q8 моку** (`b = a` проти `c = a.copy()`) я провалив, хоча ідентичне питання взяв правильно
того ж дня. Це не прогалина в знанні. Це увага під навантаженням.

## 4. Part 1 — 6 механізмів закриті, деталі в GAPS.md

`*` копіює посилання · late binding + `lambda i=i:` · `nonlocal`=enclosing, `global`=module ·
bare `*` ⇒ keyword-only · `is`/`==` + hash/eq контракт · створення ≠ виклик.

Плюс з моку, **нове і треба вивчити**:

**GIL не робить спільний мутабельний стан безпечним.** Не казати "через GIL це безпечно".
GIL — про виконання байткоду в потоках CPython. Логічні races від нього не зникають. В asyncio
таски **перемежовуються на кожному `await`** — саме там і ламається.

```python
counter = 0
async def increment():
    global counter
    current = counter          # усі 10 читають 0
    await asyncio.sleep(0)     # <-- точка перемежування
    counter = current + 1      # усі 10 пишуть 1
# запущено: counter == 1, детерміновано
```
Розділяти: OS-потоки · multiprocessing · asyncio-конкурентність · справжня паралельність.

## 5. Part 2 — головна слабкість, і вона конкретна

**`create_task` проти `await`.** Це найбільша async-діра за оцінкою моку.

```python
await coro()                      # запусти і чекай ТУТ
task = asyncio.create_task(coro)  # запланувати незалежно — вже біжить
await task                        # тільки забрати результат
```
Три `create_task` + три послідовних `await` = **час найдовшого**, не сума. Бо всі три вже
стартували до першого `await`.

**Перша спроба `fetch_all` була послідовним циклом без `return`.** Заміряно: 0.303s проти
бюджету 0.25s, `max_concurrent_seen=1`. Через `gather` — 0.101s, `max_concurrent_seen=3`.
Це рефлекс, який треба поставити руками, а не прочитати.

### `gather` проти `TaskGroup` — у моку взагалі не було, а спитати можуть

Запущено й підтверджено:
```
gather: піднімає виняток БЕЗ обгортки, сусідів НЕ скасовує (вони добігають)
TaskGroup: скасовує сусідів, обгортає в ExceptionGroup
           -> звичайний `except HttpError` НЕ ловить, треба `except*`
```
| | `gather` | `TaskGroup` |
|---|---|---|
| дитина впала | сусіди біжать далі | сусідів скасовано |
| форма винятку | bare | `ExceptionGroup` → `except*` |
| порядок | вхідний | збираю сам |
| коли | часткові результати корисні | все-або-нічого |

Решта: `asyncio.timeout` **скасовує** тіло, а не просто перестає чекати · `Semaphore` тримати
**тільки навколо I/O** · `cancel()` — це лише запит, треба `await gather(..., return_exceptions=True)`,
інакше "Task exception was never retrieved" · retry на 5xx і 429, **ніколи на 4xx**, bare `raise`,
не спати після останньої спроби, jitter обов'язково.

## 6. Part 3 — тут я найсильніший, не змарнувати

### Обов'язково сказати про ідемпотентність

Для білінгу це проблема №1 і моя найкраща карта. Якщо її немає у відповіді — головний козир
не зіграний. Формулювання: *"I took a critical send path out of a live pipeline with
idempotency enforced at the database level — a unique key on the business identity, so a retry
is a no-op instead of a double charge. Same discipline for payments, different unit."*

### Дисципліна таймаутів — не "підняти таймаут"

Загальний дедлайн, розкладений по залежностях:
```
бюджет запиту: 10s
  price/зовнішній API: 2s
  LLM:                 7s
  накладні:            1s
```
Плюс: таймаут на кожну залежність · бюджет ретраїв · загальний дедлайн · **жодного
необмеженого очікування** · зрозуміла помилка клієнту.

### Fallback не вигадує факти

Згенерована "приблизна" відповідь, яка виглядає фактичною, **гірша за помилку**. Віддавати:
```json
{"error": {"code": "LLM_UNAVAILABLE", "message": "Temporarily unavailable."}}
```
а всередину — лог справжнього винятку, метрики, трейс.

### Кеш

Ключ = **хеш нормалізованого входу + модель + версія промпту** (+ контекст, якщо є). Без моделі
й версії промпту зміна промпту тихо віддає стару відповідь. Redis, не in-process — у FastAPI
кілька реплік, у кожної свій кеш. **Single-flight**: 1000 промахів → 1 виклик апстріму, 999
чекають той самий результат.

### Concurrency тільки для незалежного

У моку я спробував паралелити виклик ціни і LLM. LLM **залежить** від ціни — паралелити нічого.
Розпаралелювати можна лише незалежні кроки.

### LLM — це ненадійна HTTP-залежність, і це чесно

Port/Protocol, таймаути, ретраї з backoff, обмежена конкурентність, **валідація виводу моделі як
недовіреного входу**, fallback, кеш, **не логувати промпти дослівно** (GDPR — Manychat обробляє
переписки кінцевих користувачів). Це і є senior-відповідь, не виправдання.
Я не ML-інженер: моделі й agent-фреймворки з нуля не будував. Go і Java — читаю, не пишу.
